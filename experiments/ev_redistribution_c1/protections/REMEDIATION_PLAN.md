## 2. Minimal code changes (proposed diffs in `patches/`, generated by `make_patches.py`)

1. **R1 — `runner_no_ev_actuals.diff`** (+22 / −12)
   - The publish list becomes a module constant `PUBLISH_FILES`: forecasts, geography, `metadata.json` and `run_report.md`, **without** `ev_actuals_*`.
   - `_publish()` raises if an `ev_actuals_` name is ever added back.
   - The runner still builds EV actuals in its own `outputs/` for its QA. The DFES/NESO forecast workflow is unchanged.
2. **R3 — `promotion_protect_c1.diff`** (+85 / −13)
   - `EV_CHANGED` no longer lists `ev_actuals_*`.
   - New `C1_PROTECTED_FILES`: promotion aborts if the candidate tree would change them.
   - New `forecast_rows_preserved()`: DFES/NESO rows must be unchanged (key columns exact, values within 1e-9 relative); only `SMMT_NOWCAST` rows may be added or replaced, and they must not be duplicated.
   - `restore_backup()` becomes a file-level restore of `PROMOTION_MANAGED_FILES` only: no `rmtree`, no deletion of other files, never the C1 files.
   - `_validate_production()` also requires the C1 files to exist.
3. **R3a / R3b — operational, no code:** quarantine the stale staged run, by removing or archiving its `outputs/integration/ev_actuals_*` (or the whole run) outside `project/`. With patch 2, backups can no longer restore EV actuals.
4. **R2 — documentation:** scripts 09/12/13 are legacy and must never be copied into `integration/`. A CLAUDE.md update needs approval.
5. **R5 — git:** after release, commit the three C1 files on their own. Install the prototype `pre_commit_c1_guard.py` as `.git/hooks/pre-commit`. It accepts a staged `ev_actuals_*` only when its LFS oid equals the bytes recorded by the latest sealed release manifest (methodology, floor, periods and provenance are checked), refuses deletions, and refuses bulk staging of `production_backups/` and `dft_staging/`.
6. **Every update validated:** EV actuals can only arrive through `c1_release.py`. Its preflight checks:
   - the methodology id and the 0.20 floor;
   - the five quarters;
   - the shadow-manifest source hashes and the byte-exact rebuild from the C1 LSOA source;
   - the pinned hashes.

   Patches 1–2 remove every other writer, and the hook checks the same manifest at commit time.

## 5. Git / LFS staging risks

- `*.csv` is LFS with `-text`, so bytes are stored exactly (CRLF kept) and hashes are stable on every platform.
  - Staging the restored forecast reuses LFS oid `6ce3d9a4…`, which already exists in history at `aa39e40`, a commit on `origin/main`.
  - Check before pushing: `git lfs push --dry-run origin main`.
- `dashboard.html` and `metadata.json` are normal git files with `core.autocrlf=true`.
  - The working copies are 100% CRLF and are stored as LF. A checkout on this machine reproduces identical bytes, so the pinned hashes hold.
  - On an LF checkout (Linux, or `autocrlf=false`) the bytes differ and the release preflight **fails closed**. Run the release on this Windows checkout, or re-pin in a reviewed change.
- **Never** use `git add -A`, `git add .`, `git add project` or `git commit -a`. These would sweep in:
  - 10 untracked `project/production_backups/*` and all of `project/dft_staging/` (Method A copies, hundreds of MB of new LFS objects);
  - 20+ tracked `__pycache__` deletions;
  - unrelated work in progress (`app_data_manager.py`, templates, `data_manager/*`).
- **Never** run `git stash`, `checkout --`, `restore` or `reset --hard` on these paths. HEAD holds the corrupt forecast and the old dashboard.
- Proposed commands (not run):
  ```
  git add -- project/output_processed/integration/monthly_forecast_dno.csv
  git diff --cached --name-only            # must print exactly that one path
  git show :project/output_processed/integration/monthly_forecast_dno.csv   # pointer oid must be 6ce3d9a4…
  git commit -m "Restore validated DFES/NESO monthly forecast (from aa39e40; fixes 97e855f corruption)"
  git add -- dashboard.html
  git diff --cached --name-only            # exactly dashboard.html
  git commit -m "EV charts: canonical filter path, own March 2025 baselines, date axes"
  ```

## 6. Archive no-write

- **Cause:** in Phase 5 I re-ran `integration_writer.py`. Its `write_all()` rewrote the shadow files and `method_a_archive/` on every run. The bytes were identical, but the files were written (modification times changed).
- **Latent bug:** after a C1 release, the same command would have copied **C1** bytes into `ev_actuals_dno_method_a_original.csv` and produced an empty pre-2025 history.
- **Safeguards implemented** (in experiment code only):
  1. The writer skips identical content, so a re-run with unchanged inputs is a strict no-write.
  2. Archive files are write-once: different bytes raise `PermissionError`.
  3. An existing archive is frozen: it is verified against its manifest and never rebuilt.
  4. The archive cannot be built when production no longer contains Method A history.
  5. `tests/conftest.py` records the sha256 **and** `st_mtime_ns` of the C1 code, the outputs, shadow files, archive, `dashboard.html`, all `integration/` files and `promotion.py` at session start, and fails the session on any content change *or* identical-bytes rewrite.
- **Two different guarantees:** byte integrity (the hash is unchanged) held in Phase 5. The strict no-write guarantee (no rewrite at all, so the modification time is unchanged) did not. The guard now enforces both.

## 8. Minimal sequence for the separately approved implementation phase

Each step is a separate approval, run in order. Stop at any failure.

1. **Baseline:** run `reversion_scan.py` (expect 4 blockers) and the full experiment test suite, and record a hash inventory.
2. **Prerequisite commit A:** stage the restored `monthly_forecast_dno.csv` only (§5). Check it is the only path in `git diff --cached`, check the pointer oid is `6ce3d9a4…`, then commit.
3. **Prerequisite commit B:** stage `dashboard.html` only, then commit. Re-run the dashboard regression suites. The pinned hashes are unchanged on this checkout.
4. **Quarantine R3a:** move `project/dft_staging/run_smmt_nowcast_20261001_121056/outputs/integration/ev_actuals_*.csv` (or the whole run) to an archive outside `project/`. Keep a hash manifest. Update `/candidates`, which has the run id hard-coded in `app_data_manager.py`.
5. **Patch R3:** apply `patches/promotion_protect_c1.diff` (`git apply --check` first), then run `test_protections.py`.
   - **Do not** run `tests/test_phase5_end_to_end.py`: it writes into the real `project/production_backups/`.
6. **Patch R1:** put `dashboard_integration/` under version control (its own repository, or this one). Apply `patches/runner_no_ev_actuals.diff`.
   - Do not run the runner yet. The next run should be planned, and checked afterwards with `verify-c1` and the forecast hashes.
7. **Re-scan:** `reversion_scan.py` must report **0 blockers**, then run the full suite again.
8. **Decide D1–D4:** `metadata.json`, nowcast display, quarantine disposal, and CLAUDE.md wording for the legacy scripts.
9. **Live release:** follow `release/RELEASE_CHECKLIST.md` (approvals; the `LIVE_RELEASE_ENABLED` change; preflight; promote; `verify-c1`; dashboard checks).
10. **After release:** commit the three C1 files (LFS) on their own. Install `pre_commit_c1_guard.py` as the pre-commit hook. Re-run `reversion_scan.py`: R5 should then report HEAD = production = C1.
